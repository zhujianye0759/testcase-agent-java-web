## Context

Structured ALL generation persists each deterministic Skill input as a task-owned work item. Completed work is already restart-safe: registration reuses the same identity, `isCompleted` skips the invocation, and acceptance is guarded by an accepted-result hash. A failed `structured_output_invalid` work is deliberately excluded from automatic transient retry because KEE has already used its internal repair attempt. The generic task retry currently changes only the top-level task to `QUEUED`; it leaves that exact work `FAILED`, so the coordinator cannot claim it and immediately fails again.

The production incident has two completed review slices and one failed zero-write review slice. Recovery must preserve the completed rows and prior attempt while making only the explicit user-selected retry eligible.

## Goals / Non-Goals

**Goals:**

- Make one explicit API call atomically recover one exact eligible failed structured work and the owning failed ALL task.
- Preserve frozen scope, parsed-unit inventory, completed work, hashes, business rows, bindings, and attempt history.
- Keep automatic transient retry unchanged and make concurrent/repeated explicit requests single-winner.
- Expose backend-computed eligibility so the UI does not advertise an operation the server cannot perform.

**Non-Goals:**

- No automatic retry of `structured_output_invalid`.
- No retry of an undiagnosed or unknown business validation failure, scope/evidence authorization failure, cancellation, lease-loss, database, or concurrency failure.
- No task cloning, document upload/reparse, OCR, PageIndex, graph, KEE, prompt, schema, or model-timeout change.
- No deletion or rewriting of prior accepted business data or failed attempts.

## Decisions

1. **Recover the exact work by an atomic repository transaction.** Lock the `generation_task` row, require `FAILED` + `ALL`, require no owned execution slot, require a frozen request/scope snapshot, and select exactly one failed structured work without an accepted hash. Outside V2 reconciliation, lock its latest attempt and require either `structured_output_invalid`, or `business_validation_failed` with a nonblank code from the separately reviewed retry allowlist and a bounded safe JSON field path. The initial business allowlist contains only `REVIEW_FACT_DIRECT_EVIDENCE_UNSUPPORTED`; membership in the broader safe display catalog is not sufficient. V2 reconciliation is governed only by the dedicated run/page recovery decisions below. Verify that the failed work owns no typed business rows or bindings. Then update only that work to `QUEUED`, clear its lease and current work/task diagnostic projection while retaining the failed attempt's immutable safe diagnostic, clear task-level terminal projection, and transition the task to `QUEUED`. Any failed predicate returns a conflict and rolls back.

2. **Do not create the new attempt inside the retry transaction.** The existing targeted `claimRegistered` creates exactly one running attempt when the durable queue reaches the deterministic identity. This keeps attempt creation coupled to worker ownership and preserves stale-attempt protection. Because the explicit transaction changes the exact work to `QUEUED`, it does not add `structured_output_invalid` to the automatic FAILED-work retry whitelist.

3. **Reuse deterministic coordinator recovery.** The coordinator traverses the frozen persisted inventory, re-registers identities, skips completed hashes, and reaches the recovered work. It does not call KEE for completed slices. Later work is registered only after the recovered work succeeds.

4. **Compute eligibility on the server.** Task detail exposes a boolean and one fixed reader-safe Chinese reason. The frontend displays retry only when eligible. The POST repeats every predicate under row locks and returns 409 for stale, concurrent, duplicate, or forbidden requests; the read projection is advisory, never authorization.

5. **Allow one model invocation per explicit retry.** An explicit retry can create one next attempt. If that attempt again ends in an eligible terminal failure, it becomes terminal and requires another explicit user action. Neither `structured_output_invalid` nor `business_validation_failed` is added to automatic transient retry. Existing in-invocation KEE repair and Java transient retry limits remain unchanged.

6. **Treat exhausted material-review capacity as a separate narrow branch.** A latest `response_too_large` attempt is eligible only when its failed work is exactly `requirement-material-quality-review` / `REQUIREMENT_MATERIAL_REVIEW`, `ordinal_start == ordinal_end`, and the frozen evidence closure contains exactly one persisted unit. The task must still have exactly one failed work; every other unfinished work must be zero-write `QUEUED`, and all existing accepted hashes and completed rows remain immutable. The advisory read and the POST use the same predicates; the POST repeats them after locking the task, unfinished work rows, and latest attempt. This branch is for a corrected KEE deployment already proved by a same-input zero-write replay; Java never truncates the unit or silently treats the capacity failure as success.

7. **Persist only allowlisted coordinator diagnostics.** The coordinator advances a local stage enum across task/state resume, session open, inventory traversal/resume, material review, function extraction/pre-split, reconciliation, and testcase/export. A generic runtime failure is mapped to a fixed exception category and stored through the existing nullable V14 diagnostic columns. The exception message, stack, request/response, material text, model output, URL, and credentials never enter persistence, logs, or the public task detail.

8. **Recover the exact queued-work residue by changing only task execution state.** A prior explicit retry may atomically queue the work, after which the coordinator can fail before `claimRegistered` creates the next attempt. The residue is eligible only when the failed ALL task has no slot, exactly one unfinished `QUEUED` work, no accepted hash, no lease, no running attempt, no work-owned business row, and a latest historical failed attempt that still satisfies the existing explicit retry allowlist. Under the same task/work/attempt locks, retry changes only the top-level task execution axes and clears its current terminal diagnostic. The queued work, historical attempt, completed siblings, accepted hashes, typed rows, bindings, artifact metadata, and result snapshot are not changed. A second concurrent caller observes the queued task and loses.

9. **Resume review and extraction as independent durable stages.** The former `hasCompletedMaterialStages` switch conflated two stages: one queued extraction made the coordinator rebuild all already accepted review windows. For historical split review rows this re-entry also reconstructed a child with split depth but no document coordinate, which the frozen-window validator correctly rejected. Recovery now checks accepted review leaves separately. A completed review stage permits a persisted registry containing inventory evidence and accepted review facts even while extraction is unfinished; it skips review entirely and executes only the extraction stage. The existing all-material predicate remains the gate for skipping extraction and proceeding directly to reconciliation. Both predicates require a complete task-owned inventory and non-null accepted hashes, so no incomplete review is silently bypassed.

10. **Recover only an exhausted transient extraction leaf.** KEE network failures are persisted through the stable public type `model_execution_failed`; Java does not infer a finer network subtype from logs. The explicit retry branch therefore requires the exact `feature-scope-reconciliation` / `FEATURE_SCOPE_EXTRACT` operation, at least the existing two bounded attempts, a latest failed `model_execution_failed` attempt, and the same zero-write, no-hash, no-lease, no-slot, single-failed-leaf predicates used by the other audited branches. `SPLIT` parents and completed siblings are deliberately excluded from the unfinished-work count and remain immutable. The POST repeats the decision under task/work/attempt locks and changes only the failed leaf and task to `QUEUED`; the targeted worker claim creates the next attempt. This is an explicit recovery action after the automatic bound, not an automatic retry-policy expansion.

11. **Rebuild only one globally invalid reconciliation staging run.** A reconciliation page can pass page-level validation while the completed run later fails the Java task-level coverage check. Explicit recovery is allowed only for the exact `feature-scope-reconciliation` / `FEATURE_SCOPE_RECONCILIATION_V2` work whose latest failed attempt and task projection both carry `RECONCILIATION_V2_RESULT_INVALID` at `$.reconciliation_run`. Under task, work, attempt, run, and page row locks, Java requires one `STAGING` run with a null accepted hash, at least one page and every page `COMPLETED`, no work lease or running attempt, no work accepted hash, no formal reconciliation/source-terminal/downstream row, and no artifact. The transaction deletes the locked page rows first so the existing V15 foreign keys cascade only their staged relations and bindings, deletes the run, and queues the same work and task. Historical attempts, frozen scope, completed upstream work, facts, findings, function items, and bindings remain immutable. The next targeted claim creates the sole next attempt; the coordinator recreates the deterministic run and pages and must call KEE because no completed staging page remains. This branch does not make arbitrary `business_validation_failed` work retryable.
12. **Resume only a zero-write reconciliation model failure.** KEE's log-only `network` category is not persisted in the Java database, so Java does not claim to distinguish network transport failures from other `model_execution_failed` causes. The durable recovery predicate instead requires the sole unfinished work to be `feature-scope-reconciliation` / `FEATURE_SCOPE_RECONCILIATION_V2`, its latest terminal attempt to be `model_execution_failed`, and its one locked run to remain `STAGING` with a null accepted hash. At least one leaf page must remain `PLANNED`; every planned page must have no completed metadata and no staged relation, while completed pages and their staging rows are preserved. No work lease, running attempt, work-owned final business row, formal reconciliation, source terminal, downstream row, or artifact coordinate may exist. One explicit user action requeues only the same work and task. It does not delete or rebuild the run, pages, or staging graph. The next targeted claim creates one new attempt and the coordinator obtains only `PLANNED` pages, so completed pages are not called again. This model-failure branch remains closed to `structured_output_invalid`, `business_validation_failed`, other Skills, and other operations; the separate ESR-013 branch governs the exact structural page state.

13. **Resume only one zero-write page-level reconciliation structural failure.** A V2 `structured_output_invalid` attempt is eligible only through this dedicated branch, never the generic structural-error rule. Under the existing task/work/attempt transaction, Java locks and rechecks the sole `STAGING` run and every page. At least one executable `PLANNED` leaf must remain; each `PLANNED` or `SPLIT` page must own no staged relation or binding, and each `COMPLETED` page must retain non-null completion metadata and result hash. All pages must share the run identity. The work has no accepted hash, lease, running attempt, owned business/audit row, formal reconciliation, source terminal, downstream row, artifact coordinate, or execution slot. One explicit action requeues only the same work and task and preserves the complete run/page/staging graph. The next targeted claim creates the next attempt and the existing pending-page query skips completed pages. If every page is completed and task-level global closure fails, only the separately diagnosed ESR-011 rebuild is eligible.

## Risks / Trade-offs

- **[Eligibility becomes stale between GET and POST]** → The POST rechecks every predicate under locks and returns 409.
- **[Queue claims immediately after commit]** → The task/work transition is one transaction; workers see either the old terminal state or the complete queued state.
- **[Completed rows are duplicated]** → Stable identity plus `isCompleted` skips invocation; acceptance retains hash-based idempotency.
- **[A failed work contains partial rows]** → Explicit retry fails closed unless all work-owned typed rows and bindings are zero.
- **[An arbitrary business error becomes retryable]** → The latest attempt must contain a code from the separately reviewed explicit retry allowlist and a bounded safe path; missing, blank, unknown, known-but-not-allowed, or unsafe diagnostics fail closed.
- **[Repeated explicit retries create unbounded automatic attempts]** → Each POST permits only one queued claim; no automatic retry loop or transient whitelist expansion is introduced.
- **[A broad capacity error becomes a random retry loop]** → `response_too_large` remains forbidden for multi-unit windows, other Skills/operations, accepted or partially written work, multiple failed leaves, active claims, and non-zero queued siblings. One explicit action only queues the exact exhausted single-unit review leaf.
- **[A generic exception leaks material or credentials]** → Only an enum code, allowlisted stage path, and fixed exception category are accepted by the persistence/logging seam; arbitrary exception text and stacks are never serialized.
- **[A failed task with arbitrary queued work becomes retryable]** → The transaction requires exactly one zero-write, lease-free queued residue plus a previously failed allowlisted attempt and repeats every predicate after row locks.
- **[One unfinished extraction replays accepted reviews]** → Review completion is evaluated independently, and the persisted registry is allowed only after every review leaf and the inventory pass fail-closed checks.
- **[A generic model error opens unrelated work]** → The transient branch is restricted to an exhausted `FEATURE_SCOPE_EXTRACT` leaf with the stable `model_execution_failed` type; other operations, first failures, partial results, active claims, and multiple failed leaves remain closed.
- **[Invalid staging is silently reused]** → The exact audited branch deletes the locked run-owned staging graph before requeue; a coordinator regression proves the rebuilt run has planned pages and performs a real KEE-port invocation rather than accepting old completed pages.
- **[A generic structural error opens V2 retry]** → Generic `structured_output_invalid` remains closed for reconciliation V2. The dedicated page-level branch proves the complete run/page/staging shape, completion hashes, zero unfinished staging, zero publication, and single unfinished work under transaction locks before requeueing only that work.
- **[Cleanup deletes valid or unrelated data]** → Eligibility requires zero formal/downstream publication and exact run ownership; deletion is ordered page-before-run, checked by affected-row counts, and covered by rollback, near-state, and concurrent single-winner tests.
- **[Legacy retry behavior regresses]** → Legacy batch retry remains in its existing transaction and receives focused regression coverage.

## Migration Plan

No schema migration is expected. Deploy the tested Java JAR, verify the live task remains unchanged and eligible, then invoke the existing retry endpoint once. Rollback is the prior JAR; persisted attempts and accepted rows remain compatible.

## Open Questions

Additional terminal failure types or diagnostic catalogs require a separate reviewed allowlist change.
