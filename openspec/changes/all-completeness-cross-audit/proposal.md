## Why（变更原因）

当前 `ALL` 将模型生成的一份 Markdown 功能清单视为完整生成范围，因此即使响应仅包含九个功能，仍可创建九个成功批次并进入 `COMPLETED`。系统需要可验证的材料覆盖台账和功能清单/需求双向审查，避免将缺失的源内容、无法说明的映射及未生成的功能呈现为完整交付。

## What Changes（变更内容）

- 在功能生成开始前，通过已开发、待联合部署验收的 KEE V1 `GET /api/v1/knowledge/{knowledge_id}/parsed-units` 契约，枚举当前最新、已授权文档已经持久化的文本 Chunk；不请求或传递历史版本参数。
- 上传和解析必须在调用前完成，且文件在任务中不处于主动替换状态。调用方若明确获知文件已替换，Java 丢弃已接收的部分结果并从第一页重新开始；不得假定或实现自动检测。
- 分页默认 50 个 Chunk，最大 100；请求超过 100 时按 100 处理。每个序列化响应页最大 4 MiB；单个 Chunk 超过该上限时返回 `unit_too_large`，不得截断文本。正常续页使用 `next_cursor`。
- Java 累计 `ordinal` 与 `total_units`，并仅在末页 `complete=true`、计数一致、单元唯一有序且游标无循环或缺口时通过材料遍历门禁。`complete=true` 只证明本次读取可见的持久化文本 Chunk 已枚举，不代表 Word、PDF 或 Excel 的原生解析保真度。
- 持久化源单元、提取出的功能候选项、双向审查结论和最终冻结功能集合的耐久覆盖台账；测试用例证据仅保留 KEE 文档/Chunk 引用。
- 双向审查：仅存在于需求中的功能记为 `功能清单遗漏`；仅存在于功能清单中的功能记为 `需求未覆盖该功能点`；冲突、重复、拆分、合并和证据不足均保留为可追溯的候选发现。
- 每个有界审查单元、最终双向核对和单功能生成批次均先创建独立的 Skill 准备会话：审查显式传入 `feature-scope-reconciliation`，生成显式传入 `functional-testcase-design`；准备和业务请求仅走 KEE `isolated-skill` 专用入口，且每次调用均以同一 ID 的 `read_skill` 声明、精确参数、成功结果及完成终态为接收门禁。旧 agent-chat 404 不回退；非 `read_skill`/`execute_skill_script` 工具直接失败关闭。任一准备失败均拒绝整个当前审查或生成阶段，不继续领取后续单元或批次。
- 仅在每个源单元和候选项均已有终态结论后冻结最终功能集合；重试复用该冻结集合。
- 对每个可生成的冻结功能生成一个隔离批次，且恰好接收一个正向和一个反向测试用例。
- 仅在源覆盖、审查收敛、冻结范围、所有批次结果及 `2N` 测试用例不变量均通过时，才允许进入 `COMPLETED`。
- 最终双向核对以全量候选上下文、每个功能审核批次最多 8 个代表目标执行；每个批次经严格合同验证后以稳定锚点在 Java 端归并。仅当同一批次三次尝试的每一个封闭类别都属于批准集合 `MISSING_TARGET`、`REPRESENTATIVE_BINDING`、`BUSINESS_PATH_STRUCTURE`（可混合）时，丢弃该批次全部未接收响应并按原稳定顺序对每个代表目标逐项执行隔离核对；任何一次 `STRICT_MARKDOWN`、`ANCHOR_CONFLICT`、`NORMALIZED_PATH_CONFLICT`、`UNKNOWN_CONTRACT` 或其他非批准类别均不得逐项核对并直接失败关闭。每项仍携带全量候选上下文和精确目标绑定、复用既有 parser/path/anchor/cross-page 校验、至多三次；全部逐项通过才原子合并，任一失败均不持久化部分结果。Java 不自动修正模型分类、路径或来源坐标，且不降低冻结或 `2N` 门禁。最终详情、Markdown 和工作簿确定性清理 `documentId`、`unitId`、`candidateIds`、`groupAnchorId` 机器绑定，不得恢复已废弃的模型 JSON 协议，也不得新增技术工作表。
- 真实 V2.0 联调第 22/30 个功能审核批次三次因非“拆分”结论在对象/功能点列拼接 `<br>` 加章节号而触发业务路径结构门禁。最终核对初始提示和该固定错误的重试提示均明确：章节号、条款号和目录编号只能留在证据对照列；非拆分路径必须为单一业务功能名，不得复制证据中 `<br>` 后的编号。Java 继续拒绝该响应，不裁剪模型结果；单次失败或未满足同一批次三次均属于批准集合时不得逐项复核，只有满足该累计条件时该类别才参与逐项重做。
- 真实 V2.0 联调第 15/30 个功能审核批次的前两次严格重试因目标覆盖不完整、第三次因代表证据绑定失败而关闭，未冻结范围。最终核对的本批次代表目标区必须在同一行给出其精确 `candidateId`、`documentId` 与 `unitId`；初始和代表绑定错误的固定重试提示均要求逐字复制同一目标绑定行，禁止从全量上下文中的同名/同路径邻居复制来源坐标。Java 继续拒绝错绑响应且不重写坐标；单次失败或未满足同一批次三次均属于批准集合时不得逐项复核，只有满足该累计条件时该类别才参与逐项重做。
- 展示面向业务的材料、审查、冻结功能和测试用例进度，但不暴露文档 ID、源游标或内部功能 ID。
- 最终双向核对功能审核批次在三次严格重试耗尽时，仍以批次序号、总批次数、尝试次数和封闭失败类别形成任务结果摘要；用户可见的“功能审核批次”不是 PDF、Word 或 Excel 的源文件页。内部技术字段和诊断日志可保留 `page` 命名；同时以任务、阶段、页和尝试关联的持久化滚动诊断日志记录提示词、SSE 终态 Markdown 与校验失败上下文，供受控运维定位。日志绝不记录 API Key、密码或鉴权头，也不进入共享任务详情或下载制品。
- 同一功能审核批次内出现 `NORMALIZED_PATH_CONFLICT` 时，bulk 第 2/3 次按每个冲突组仅向模型提供该组全部 `targetCandidateId`、按全量稳定候选顺序确定的 `earliestTargetCandidateId`、同一实际值的 `requiredGroupAnchorId` 和固定规则；不得回灌未接收回包的路径、分类或正文。模型若仍判断为同一路径，必须令所有行分类/完整路径一致，且每行 `groupAnchorId` 逐字复制该组 `requiredGroupAnchorId` 的实际值；若判断不同，必须以正式证据给出真实可区分路径和各自合法 anchor。Java 不自动语义裁决或改写；跨批已接受先例继续使用既有精确绑定。该类别保持非批准，三次耗尽失败关闭且零逐项复核。
- 同一功能审核批次若当前已投影行将 `groupAnchorId` 指向已接受前批候选、但分类或完整路径未逐字等于该 accepted anchor，`ANCHOR_CONFLICT` 的第 2/3 次反馈仅为每个错误当前目标输出 `targetCandidateId`、`rejectedGroupAnchorId` 与同一当前目标的 `requiredSelfAnchorId`。若不逐字复用已接受先例区的分类和完整路径，必须将 `groupAnchorId` 逐字复制该实际 self-anchor；若确属旧语义组，必须逐字复用分类、完整路径和旧 anchor。不得回灌未接收回包的业务文本、分类、路径或正文，Java 只验证不裁决或改写。该类别仍非批准，三次耗尽失败关闭、零逐项复核、零持久化。
- 已接收生成批次的 Markdown、两条用例行和成功尝试保持耐久；任务重试只重新领取未接收/失败批次，不能重新调用已接收的冻结功能。最终核对的页级持久断点不属于本期。
- 真实 V2.0 联合验收中，175 个冻结功能已有 132 个批次和 264 条测试用例原子接收，剩余 43 个批次因固定 Markdown、编号或冻结证据合同失败而未发布残缺工作簿。后续仅对这些失败批次创建第 2/3 次尝试，并依据紧邻上一失败尝试的安全原因追加白名单固定纠错提示；不得将任意失败原文、模型响应、异常、URL 或凭据回灌提示词。首轮 ALL 提示和既有指定功能模式保持不变，已接收 132 个批次不得再次调用或覆盖。
- 上述失败批次第 2 次尝试后已有 161 个批次和 322 条测试用例接收，剩余 14 个失败均为模型把“依据通用经验，待确认”与 `<br>candidateIds` 正式证据写在同一单元格。第 3 次尝试前只将该固定纠错提示消歧为互斥二选一：正式材料使用可读摘要与允许的 `candidateIds`，通用经验单元格只保留固定文案并立即结束，严禁追加 `<br>`、证据标记、引号、句号或其他文字。校验器和已接收数据保持不变。
- 将增量、通用的 KEE 解析材料单元读取 API 作为外部前置条件。只读验证已证明 `/preview` 文本稳定，但无法证明当前读取中已持久化解析文本 Chunk 的完整枚举；原生解析保真度另以代表性 PDF、DOCX 和 XLSX 样本验收。

## Capabilities（能力）

### New Capabilities（新增能力）

- `structured-material-read`：通过固定的 KEE parsed-units HTTP 合同将当前最新的已授权 KEE 文档读取为可分页的持久化文本 Chunk；对范围失败、遍历缺口、重复、乱序、计数不一致、游标错误、超大单元或截断实行失败关闭。
- `kee-skill-invocation`：按业务阶段请求两个精确的测试专业 Skill，并以 SSE 工具事件验证 `read_skill` 成功；不引入 Skill 版本、哈希、manifest 或新 Skill API 依赖。
- `bidirectional-feature-audit`：在功能清单条目和需求功能之间构建完整的交叉审查台账，包括遗漏、冲突、拆分、合并、重复和证据不足。
- `complete-all-generation`：冻结可审计的最终功能集合，为每个可生成的功能恰好生成一个正向和一个反向测试用例，并施加如实的任务/导出完成门禁。
- `completeness-web-reporting`：在隐藏技术范围标识符的同时，展示面向业务的覆盖情况、审查情况、生成进度及结果不完整的原因。

## Impact（影响）

- Java Web：KEE 适配器端口、任务流程/状态校验、MySQL/Flyway 持久化、Markdown 发现/审查解析、批次校验、Excel 汇总、任务 API 及 Vue 任务详情进度。
- KEE：`add-parsed-document-structure-api` 与 `add-testing-professional-skills` 已在独立分支完成开发、review、定向验证、真实运行验收和回滚演练，但尚未合并、推送或归档，当前运行环境已回滚旧镜像。Java 在本 change 中以 WireMock 固化消费者合同；真实联合验收时临时部署这两个 KEE change。它们不得修改 RAG 检索、排序、重排序、PageIndex、Wiki、普通 Agent/SSE 或最终回答行为。
- 证据：既有 KEE 文档/Chunk 证据始终是唯一正式证据模型；Java 覆盖台账只引用该证据，不创建第二套来源证据模型。
- 数据：新增应用自有的审查和冻结功能记录；KEE 数据库保持外部边界，绝不复用。
- 兼容性：指定功能生成以及现有两张 Markdown 表/两个 Excel Sheet 保持兼容。不会改写既有已完成制品。
