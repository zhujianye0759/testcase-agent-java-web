## Context（上下文）

当前 `ALL` 路径仅向配置的 KEE 智能体请求一次两列表的 Markdown 功能清单，接收任意非空且序号为正整数并互不重复的集合，冻结这些行，并在所得批次均未失败时将任务标记为完成。因此，已完成的 V2.0 任务 `1d768085-af64-4c5f-9299-b27042249c44` 虽然所选功能清单包含远多于九条的源条目，且需求文档存在额外功能章节，仍接收了九个发现功能并导出了十八个测试用例。

一次只读可行性验证使用精确的 V2.0 范围，未改变任何 KEE 状态。对每个 `/knowledge/{id}/preview` 响应进行两次读取，结果字节完全一致。功能清单 preview 暴露了 1 至 128 的序号，但因序号 113 出现两次而得到 129 个记录形态匹配项。工单 preview 暴露了截至 `4.2.2.2.6.6.1` 的 100 个唯一编号章节。然而，`/preview` 是当前已启用 Chunk 的拼接结果，未暴露总单元数、游标或显式完成标记。它不能证明当前读取可见的全部已持久化解析文本 Chunk 已被遍历和审查，更不能证明原始文件的页、Sheet、行、单元格或章节坐标。已部署的 `/chunks/{id}` 路由对当前服务凭证返回 404，不能作为可用的回退契约。

此 change 涉及多个模块，但仍是一个编排 change。KEE 继续负责 Office/PDF 解析和源授权。Java Web 负责材料覆盖、审查收敛、任务耐久性、冻结生成范围和如实完成。模型生成内容仍为 Markdown。

## Goals / Non-Goals（目标/非目标）

**目标：**

- 在 `ALL` 生成前，使每一份当前最新、已授权源文档的已持久化文本 Chunk 枚举均可审计。
- 双向交叉审查功能清单候选项和需求候选项。
- 保留可追溯的遗漏、冲突、拆分、合并、重复和证据不足结论。
- 冻结稳定的最终功能集合，并为每个可生成的功能恰好接收一个正向和一个反向测试用例。
- 防止任何未读取、无法说明、未生成、被截断、遍历失败或格式错误的工作进入 `COMPLETED`。
- 保持浏览器流程简单，导出限制为现有两个业务 Sheet。

**非目标：**

- 恢复 `testcase-agent.response.v1`、`generation-result-1.0` 或其他任何模型 JSON 输出契约。
- 在 Java Web 中解析原始 Excel、PDF、Word、OCR 或图像。
- 将 parsed-units 的 Chunk 枚举完整性误称为原生解析保真度；后者另以代表性 PDF、DOCX 和 XLSX 样本验收。
- 为历史版本增加参数，或通过比较内容标识、摘要或自动替换侦测控制本次遍历。
- 修改 KEE 检索、排序、重排序、PageIndex、Wiki、Agent 循环、提示词路由或最终回答行为。
- 新增第三个工作簿 Sheet、审批流程、人工功能审查门禁、登录、角色或权限管理 UI。
- 声称语义模型判断在数学上绝对正确。此处的保证是：不完整处理不能被表示为完整。

## Decisions（决策）

### 1. 采用 KEE V1 parsed-units 合同，而不将 preview 视为清单 API

独立 KEE changes 已完成开发、review、定向测试、真实运行验收和回滚演练，但尚未合并、推送或归档；当前 KEE 已回滚旧镜像。因此，本 Java change 以确定性 WireMock fixture 实施消费者合同，真实联合验收时临时部署 KEE changes。读取端点固定为 `GET /api/v1/knowledge/{knowledge_id}/parsed-units`。它在每一页复用现有 API-key、tenant、KB、系统、版本、材料类型、可选项目和文档白名单约束，越界仍按既有 `forbidden` 失败关闭。它返回确定性的服务 JSON envelope；这不是模型响应契约。

响应 `data` 仅包含 `knowledge_id`、`total_units`、`units`、`next_cursor`、`complete`。每个 `unit` 仅包含 `unit_id`、`chunk_index`、`ordinal`、`content`、`start_at`、`end_at`。端点只读取当前最新、已授权文档已经持久化的 text Chunk，不接受历史版本、revision、hash 或 snapshot 参数，也不返回它们。正常请求分页默认 50 个单元，最大 100；请求超过 100 时按 100 处理。正常续页使用不透明 HMAC keyset `next_cursor`。每个完整 JSON 响应页最大 4 MiB；若单个单元本身超过该上限，服务返回 `unit_too_large`，并且绝不截断文本。显式业务错误包括 `document_not_ready`、`cursor_signing_unavailable`、`invalid_cursor`、`document_not_current`、`parsed_unit_integrity_error` 和 `unit_too_large`。`complete=true` 只证明本次读取可见的持久化 text Chunk 枚举完成；它不提供或保证 PDF/Word 页、Excel Sheet/行/单元格、原生结构或解析保真度。原生解析保真度另以代表性 PDF、DOCX 和 XLSX 样本验收。

上传与解析必须在调用前完成，且文件不在任务运行中主动替换。Java 必须从无游标的第一页开始，在每页范围和文档白名单校验通过后，验证 `knowledge_id` 一致、`unit_id` 全局唯一、`ordinal` 严格连续为 `1..total_units`、游标无循环或缺口。仅当累计单元数恰好等于 `total_units`，且最终页 `next_cursor=null`、`complete=true` 时，才可将“已遍历解析材料”门禁置绿并冻结材料清单；任一页 HTTP、JSON、范围、游标或单元完整性失败均使整次遍历失败。解析文本中展示的业务序号允许重复，Java 将其作为不同候选出现保留，而不把它误当作接口单元的唯一标识。

若调用方明确获知文件在本次遍历中被替换，Java 丢弃已接收的部分结果并从第一页重新开始。系统不比较内容标识，也不推断文件是否变化；没有该明确输入时，不产生替换结论。`/preview` 仍可用于展示和诊断，但不是完整性来源。

备选方案：在 Java 中解析 preview Markdown。已拒绝，因为 preview 无法证明源单元覆盖，且原始文档解析属于 KEE。备选方案：依赖 Agent `list_knowledge_chunks` 工具。已拒绝，因为工具调用由模型控制，chunk 覆盖不是耐久的外层循环保证。

### 2. 在语义审查前持久化源覆盖台账

应用数据库独立于模型输出保存源清单：

- `material_inventory_unit`：文档角色、既有 `chunk_id`、`ordinal`、文本和已接收处理状态；
- `feature_source_candidate`：从一个功能清单或需求解析单元提取出的候选项及其既有 KEE 文档/Chunk 证据引用；
- `feature_review_conclusion`：双向映射和终态审查结论；
- `frozen_feature_target`：最终功能标识、源候选项、拆分/合并原因、可生成性和稳定顺序；
- 用于可安全重启、幂等单元处理的审查工作项和尝试记录。

该台账只记录接收和处理状态，绝不成为第二套来源证据模型：正式业务证据始终使用既有 KEE 文档/Chunk 引用。冻结后，任务范围、提示词/Markdown 契约版本和冻结功能集合均不可变。调用方明确报告替换时，按本 change 的重启规则重新读取和审查；其他材料遍历错误使任务失败，而不是混合部分结果。

### 3. 扫描有界源单元，再执行双向审查

Java 控制处理哪个源单元，并为每个单元记录终态结果。它绝不发送无界的整份文档，也绝不要求一次调用证明其已读取全部内容。

功能清单扫描从每个解析单元中的功能条目产生候选项，保留重复展示的业务序号或文本出现而不按序号去重。需求扫描对每个稳定单元处理两次：第一遍提取动作/对象/条件候选项，第二遍检查同一解析单元中第一遍未覆盖的功能性陈述。未收敛的单元将在有界预算内重试，否则审查失败。

同一耐久扫描工作被重领时，认领事务只读取该工作最近一条已持久化失败摘要。它不是模型上下文的透传通道：第二次和第三次均附加同一份固定、全面的 Markdown 格式基线，以免模型在标题、HTML、列数和坐标之间来回摆动；只有白名单中的严格合同错误才额外转换为固定重点提示。基线只能以自然语言指向本次提示已提供的坐标标记，不含占位符或动态坐标值。首次没有该提示，未知、空或缺失摘要只使用全面基线。任何原始异常、URL、路径、凭据或机器标识均不注入提示词。该反馈不改变扫描器、最终双向核对、三次上限、失败关闭或不可变台账。

源扫描后，Agent 提出语义关系，Java 持久化并校验其覆盖：

- 匹配；
- 对仅存在于需求中的功能标记 `功能清单遗漏`；
- 对仅存在于功能清单中的功能标记 `需求未覆盖该功能点`；
- 描述冲突；
- 粒度不匹配和拆分；
- 重复和合并；
- 证据不足且不可生成。

每个源候选项必须具有恰好一个终态处置，并且必须映射到冻结功能或已记录的不可生成结论。完全相同的源重复项仍作为发现可见；语义合并建议不得消除来源追溯信息。

### 4. 仅在审查台账完整后冻结并集

最终集合是经可追溯的拆分、合并和去重决策后的功能清单与需求功能的并集。稳定功能标识源自冻结的文档/Chunk 证据引用集合和归一化业务路径，而非模型序号。重试复用冻结功能 ID、顺序、来源和审查结论。

在所有清单单元和候选项均处于终态且稳定功能集合已耐久化前，不创建任何生成批次。后续批次响应不得引入新功能或改变冻结映射。

### 5. 按阶段准备测试专业 Skill 会话，并保持模型输出为严格 Markdown

双向审查阶段在隔离 Skill 入口请求中仅传入 `skill_names=["feature-scope-reconciliation"]`；冻结单功能生成阶段仅传入 `skill_names=["functional-testcase-design"]`。每个材料单元、最终双向核对和单功能生成批次先以其冻结范围创建独立准备会话；准备 turn 的 `query` 固定为非检索 token `你好`，避免 KEE 将准备说明预执行为 RAG，而精确 `skill_names` 是服务端可用范围约束。准备和业务请求一律使用 `POST /agent-chat/{session_id}/isolated-skill`，旧入口的 404 不得回退。Java 在每次隔离 SSE 的同一 `tool_call_id` 上观察精确 `read_skill` 的声明、参数补齐、成功 `tool_result` 配对及显式完成终态；除 `read_skill` 和可选 `execute_skill_script` 外的任意工具均失败关闭。不得跨材料单元、最终核对或功能批次复用会话，以避免历史上下文串扰和无界增长；每个业务流仍须有显式完成终态。这样不把 92 个材料单元都交给模型临场决定是否读取同一规则，也不把固定 token、提示词或普通回答误作 Skill 证据。

准备失败时，Java 只对连接、超时或 408/429/502/503/504 等明确暂态传输错误，最多以三个新的隔离会话进行有界重试；范围、HTTP 永久错误、SSE/Markdown 合同、准备流任意 `error`、错误或缺失的精确 Skill 证据及准备阶段任意非 `read_skill` 工具调用均立即失败关闭。每次仍必须重新观察真实 SSE 工具成功事件，绝不将前一会话的证据移植到下一会话。任一材料审查单元或最终核对的准备失败会记录该项失败并终止当前审查阶段，由上层将任务置为 `FAILED`，不得继续领取后续审查单元；生成准备耗尽会终止当前任务而不继续后续批次。会话、Skill、智能体、材料类型或冻结范围任一不匹配均失败关闭。Java 不配置 KEE sandbox mode，也不依赖 Skill 的版本、哈希、manifest、outcome 或新 list/read API DTO。前者只负责清单/需求双向核对和最终生成范围建议，后者只对 Java 已冻结的功能设计用例。

内部扫描/审查调用使用由 Java 提供源单元标识符的、刻意保持较小的固定 Markdown 表。最终生成响应必须且只能包含两个 H2：`## 需求与功能清单审查发现`、`## 测试用例`；紧随其后的表头必须分别精确为 `序号｜对象/功能点｜问题分类｜证据对照` 与 `用例名称｜功能模块｜前提约束｜执行步骤｜预期结果｜对应需求内容`。表内多项仅用 `<br>` 分隔。Java 拒绝 JSON、代码围栏、标题/列改名、缺表、多表、少表、额外业务表或额外列。每次生成调用恰好接收一个冻结功能及其已授权源上下文。

Java 仅在下列条件均满足时接收一个批次：

- 响应到达显式 SSE 完成终态事件；
- 固定 Markdown 表解析成功；
- 测试表恰好包含当前冻结功能的两行；
- 一行名为 `<功能名>_正向`，另一行名为 `<功能名>_反向`；
- 步骤和预期结果非空，并保留成对编号；
- 需求文本和审查证据保持在已确认的正式文档/Chunk 引用范围内；
- 通用例外内容精确标记为 `依据通用经验，待确认`，而不得呈现为正式需求事实；Good/Bad 示例只能影响方法与结构，绝不作为正式业务证据。

第一个 Excel Sheet 从耐久主审查台账生成，而不是盲目追加重复的单批次 `未发现问题` 行；“证据对照/对应需求内容”沿用 KEE 现有问答来源的文档/Chunk 引用。第二个 Sheet 从已接收的测试用例行生成。工作簿严格保持两个 Sheet，不建设第二套来源证据。内部单元审计所需 `documentId`、`unitId`、`candidateIds` 在任务详情、最终 Markdown 和工作簿投影前确定性移除；导出器仍看到该 token 时拒绝导出，而不能仅隐藏页面字段。

### 6. 将完成设为跨阶段不变量

`AUDITING` 具有耐久的业务子阶段：材料清单、功能清单扫描、需求扫描第一遍、需求扫描第二遍、双向核对和功能冻结。

`COMPLETED` 要求以下条件全部满足：

- 每份当前最新、已授权源文档均在每页严格范围和文档白名单校验下读取，且仅在唯一且有序的 Chunk 已收齐、累计数量等于 `total_units`、末页 `complete=true` 且无游标循环/缺口后通过已遍历解析材料门禁；
- 每个源单元均恰好一次被接收，且两遍需求扫描均处于终态；
- 每个源候选项均有一个终态审查结论；
- 不存在未解决的冲突或映射；
- 大小为 `N` 的最终功能集合已冻结；
- 每个可生成的功能均有一个已接收批次；
- 每个已接收功能均贡献恰好两行测试用例；且
- 工作簿回读校验成功。

仅在材料台账和冻结集合完整后，当已记录为证据不足的功能无法生成或生成批次永久失败时，才允许进入 `PARTIAL`。若暴露其制品，制品必须明确说明覆盖不完整，且仅包含完整审查 Sheet 和已接收的测试用例行。清单缺口、游标错误、计数不一致、超大单元、截断、扫描未收敛或未解决映射均为 `FAILED`，且不生成制品。`CANCELLED` 保留耐久工作，但绝不将其呈现为完整。

### 7. 保持常用 Web 路径面向业务

创建表单保持不变。任务详情展示阶段及材料单元已处理数、功能清单候选项、功能清单遗漏、需求未覆盖的功能点、冲突、合并/拆分计数、冻结功能和已生成测试用例进度等计数。它不暴露 KEE ID、单元 ID、游标、提示词、原始 Markdown 或模型协议字段。材料读取失败消息只使用遍历、游标、计数或超大单元等业务可解释原因，不得称为版本漂移。

## Risks / Trade-offs（风险/权衡）

- **[当前 KEE 镜像已回滚]** → Java 先以 WireMock 和确定性 fixture 验证已冻结的消费者合同；真实联合验收仅在临时部署两个已验证 KEE change 后执行，期间不得弱化 Java 门禁。
- **[两遍需求扫描增加成本和时长]** → 使用有界耐久工作项、五个任务槽位、可恢复尝试和每调用预算；第 1 阶段没有产品时长限制。
- **[模型可能对语义拆分/合并决策产生分歧]** → 要求源完整覆盖，保留全部来源追溯信息，在有界范围内重试未收敛情形，并应失败而非静默丢弃候选项。
- **[功能清单重复展示序号或格式错误会放大候选项]** → 保留每次候选出现，报告异常，仅通过显式结论合并。V2.0 序号 113 重复是必需的回归用例。
- **[单个 Chunk 超过页上限]** → 返回 `unit_too_large` 并失败关闭；不得以裁剪文本换取完成状态。
- **[部分制品可能被误解]** → 将任务和工作簿标记为不完整，暴露原因，且绝不使用通用的已完成措辞。
- **[新增审查表增加持久化量]** → 分页读取和 repository 查询；仅保存可复现所必需的有界源文本和文档/Chunk 引用，不保存原始二进制文件。

## Migration Plan（迁移计划）

1. 固化已完成 KEE change 的消费者 HTTP/SSE 合同；当前运行镜像保持回滚状态，Java 不修改 KEE。
2. 为清单、候选项、结论、冻结和可恢复审查工作添加 Java RED 测试及 Flyway 表。
3. 编写 WireMock 消费方 fixture，覆盖固定 URI/DTO、每页严格范围和文档白名单、默认/最大/超限收敛分页、4 MiB 页上限、所有显式业务错误、`unit_too_large` 不截断、唯一有序 Chunk、`ordinal`/`total_units` 计数、仅末页 `next_cursor=null`/`complete=true`、游标循环/缺口，以及调用方明确报告替换后的首页重启；并为两个精确 Skill 的 `read_skill` 成功/缺失/失败 SSE 事件编写 fixture。
